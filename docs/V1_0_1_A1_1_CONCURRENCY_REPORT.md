# V1.0.1-A1.1 Post-Optimization Concurrency Verification Report

## 1. Current Stage B Execution Flow
Stage B (Structured Extraction) receives unstructured markdown from Stage A. It splits this markdown into manageable chunks and feeds them into a local worker pool. The pool processes chunks bounded by a fixed maximum concurrency to extract job opportunities using the AGY LLM runner.

## 2. Chunk Creation Strategy
Unstructured markdown is split by lines (`\n`) and aggregated into chunks. A new chunk is created when appending a line causes the current chunk to exceed `6000` characters. This prevents individual chunk LLM prompts from becoming too large and timing out.

## 3. Chunk Scheduling Strategy
Chunks are mapped into queue items containing the chunk text and a `queuedAt` timestamp. A predefined number of async workers (the pool size) continually pull from this queue (`queue.shift()`) until it is empty. If the mission is canceled via `abortSignal`, workers gracefully exit their loop.

## 4. Previous Maximum Concurrency
In V1.0.1-A1, Stage B utilized a simple `Promise.all` across the array of created chunks. The maximum concurrency was unbounded, matching the number of chunks created (e.g., if a massive markdown document created 50 chunks, 50 simultaneous AGY processes were launched).

## 5. Current Maximum Concurrency
`MAX_STAGE_B_CONCURRENCY` is strictly capped at `2`. The number of simultaneous chunk-processing loops will never exceed 2 per ingestion run.

## 6. AGY Concurrency
Because each chunk worker spawns exactly one `runAgyTask`, the active AGY process count generated by Stage B is safely bounded to `MAX_STAGE_B_CONCURRENCY` (2). System resources (CPU, Memory) and API constraints (rate limits, quota) are now fully protected.

## 7. Worker Pool Implementation
The worker pool uses a standard async queue loop within `src/lib/pipeline/ingestion.ts`:
- An array `results` stores outcomes.
- An array of `workers` is created up to `Math.min(MAX_STAGE_B_CONCURRENCY, chunks.length)`.
- Each worker recursively pulls from `queue.shift()` and runs `runAgyTask`.
- Variables track `activeAgyProcesses`, `peakAgyProcesses`, and `chunksCompleted`.

## 8. Telemetry Added
The existing `STAGE_B_TELEMETRY` payload was significantly extended. It now tracks:
- `chunksCreated`: Total number of chunks generated.
- `chunksCompleted`: Total chunks successfully processed.
- `activeChunkWorkers`: Count of workers initialized (max 2).
- `peakChunkWorkers`: Peak workers initialized during execution.
- `activeAgyProcesses`: Should be 0 at event recording time.
- `peakAgyProcesses`: The maximum concurrent AGY requests active at once (<=2).
- `queueWaitTime`: Cumulative wait time (ms) chunks spent in the queue before processing.
- `averageChunkLatency`: Average execution time (ms) per chunk.

## 9. Stress Test Results
A deterministic test (`stage-b-concurrency.test.ts`) was added that forcefully feeds an artificially large 120,000+ character markdown block simulating over 20 chunks. 
- **Workers Spawned:** 2
- **Peak AGY Processes:** 2
- **Chunks Generated:** > 15
- **Conclusion:** The unbounded launch vector is verifiably closed.

## 11. Tests

## 12. Build
`npm run build` succeeds cleanly.

## 13. Remaining Limitations
While Stage B concurrency is now bounded per-run, there is currently no global concurrency limiter preventing *multiple concurrent runs* from each spawning 2 AGY processes. If 10 active hunts hit Stage B simultaneously, up to 20 AGY processes could theoretically launch. A global AGY semaphore or job queue would be required to throttle at the application level.
